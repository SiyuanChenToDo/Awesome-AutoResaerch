原生 `sage autonomous` 将多研究者协作放入同一个 CORAL 管理器：默认四位研究者、两轮互评。每位研究者有自己的原生 DSH 会话、Git 工作区和候选历史，共享管理器维护的论文与证据服务。现有文献、构思、评审等模块拆分和证据卡类别保持原样。

这份文档描述接入协议和验收要求。四研究者、两轮互评的核心团队闭环已完成一次真实运行，见[运行验证与未解决问题](native-team-validation-20261018.md)。实现存在、离线契约通过、真实服务运行成功和科研质量改善分别记录。此前 run-10 是单主研究者运行，不能追溯改称四研究者讨论。

## 启动与身份

```bash
python -m sage autonomous --allow-live \
  --researchers 4 --discussion-rounds 2 \
  --output projects/team-conjectures-001
```

`--researchers` 可设为 1–4，`--discussion-rounds` 为 1–3。单研究者模式保留原来的独立构思与批评流程。多研究者模式使用 CORAL 的公开 `agents.assignments` 配置，每个 assignment 提供自己的 `research_slot` 和 `research_team_size`，由同一个自定义 DSH runtime 启动。

CORAL 分配实际 agent 名称和工作区；runtime 只在收到并校验原生 `session` 事件后向管理器注册 slot、agent ID、绝对工作区和会话 ID。各 slot 的研究工具身份由管理器派生令牌绑定，工具参数不能随意选择自己的身份。原生会话续接继续使用原来的精确 ID 恢复机制。

正式评分额外核对 CORAL 管理器交给私有 grader 的 `Task.metadata.agent_id`：只有它与注册名册 slot 0 的 agent ID 一致时才允许评分。该身份经管理器私有 socket 传递，不从候选稿中的自述身份取值；其他研究者即使复制了合法综合稿和相同 SHA，也不能代替协调者提交正式评分。HTTP 研究工具通道始终不能执行正式评分。

各工作区使用同一非 root 宿主账户。独立工作区和会话用于分开研究上下文，不构成研究者之间的操作系统权限隔离；代理应通过团队工具访问冻结提案，不能绕过协议读取同伴对话或修改同伴文件。管理器的私有证据与正式 grader 权限边界继续单独保留。

## 研究流程

| 阶段 | 研究者行动 | 管理器约束 |
|---|---|---|
| 独立提案 | 依据分配的研究视角调研、读取、提出有来源的候选 | 每人至少 `ceil(8/N)` 个；全部初稿齐备前不向同伴展示 |
| 冻结互评 | 阅读指定同伴的固定版本，提出事实或方法问题 | 固定 target 与 proposal SHA；同轮互评全部完成后才能修订 |
| 明确修订 | 对每个问题采纳、拒绝或保留未知，并说明依据和变化 | 保留问题、决议、修订文件和前后版本哈希 |
| 下一轮 | 根据新冻结版本再互评与修订 | 按配置轮数推进，不把同一份重复回复算新轮 |
| 综合 | slot 0 比较全部最终候选，保留来源并选择幸存者 | 覆盖所有原候选；只有综合对应的精确 SHA 可进入正式评分 |
| 批评与交付 | 协调者对已登记综合谱系累计取得至少两次完整建议性评阅，其中至少一次针对当前精确稿件；中文报告随稿更新 | 修改最终文件后必须重新登记综合并取得当前 SHA 的评阅；程序核对协调者身份、完整评阅和报告绑定；2026-10-18 早期团队运行未满足这项后续门禁，见验证记录 |

总候选目标为 8–12 个，由团队分摊，四位研究者通常各 2–3 个。它是提示词目标，程序执行的是每人至少 `ceil(8/N)` 个和保留全部来源候选的下限契约；2026-10-18 早期团队运行实际保留 14 个，不能写成已严格满足 8–12 上限。总检索与中心论文阅读要求继续沿用原流程；共享证据卡不意味着每人亲自阅读全文。初稿屏障用于保留独立起点，后续讨论允许明确共享来源和反证。

环形互评目标由管理器依据 slot 和轮次指定，零起始 slot、第一轮为 1 时，目标为 `(slot + 1 + (round - 1) % (N - 1)) % N`。因此两人多轮讨论仍相互评审，不会在第二轮评到自己；研究者通过状态响应读取权威的下一步，不能自行选择易通过的同伴。来源库共享，但初稿、评审与修订是冻结快照；服务端保存历史，代理改动本地文件不会追改已提交版本。

初稿屏障也覆盖 `evidence` 工具：在全部初稿齐备前，它只返回请求者自己的批评收据，隐藏其他研究者的批评，避免从批评输入间接读到同伴的初稿。论文题录、证据卡与检索记录继续共享。慢检索、正文读取与模型调用不占用团队状态的全局锁，其他研究者可继续查询状态；这一点通过无付费调用的阻塞事件测试检查。

## 工具契约

原生研究 MCP 增加 `team`，其 `action` 为：

- `status`：返回当前 slot、角色、阶段、轮次、等待情况和可读取的冻结提案。
- `propose`：通过 `artifact_path` 提交自己的初稿 JSON。
- `review`：指定当前 `round`、`target_slot`、冻结 `proposal_sha256` 与 `issues`。
- `revise`：指定当前 `round`，提交修订文件和逐问题 `decisions`。
- `synthesize`：slot 0 登记最终稿精确版本。

问题字段为 `id`、`candidate_id`、`kind`、`problem`、`repair`、`source_ids`、`target_fields`；`target_fields` 指定要修复的科研字段，`kind` 区分有文献依据的事实问题与需要论证的方法问题。决议字段为 `issue_id`、`decision`、`reason`、`source_ids`、`change`；`decision` 为 `accepted`、`rejected` 或 `uncertain`。问题成立而建议错误时，应说明替代修复；不要求接受错误建议。字段齐全本身不证明论证正确。

2026-10-19 起，原生入口默认另行审计每条同伴意见的“问题是否成立”和“修复是否有帮助”。`status` 返回当前收到的 `peer_advice_audits`；审计 pending 时返回等待，不能提前修订。原生决议还须填写 `problem_assessment`、`remedy_assessment`、`audit_response`、`remaining_uncertainty`。unavailable 明确保留为不可用，不能当作通过；研究者须对意见作出有理由的判断。此审计与数值评分/新颖性评阅分别记录，不是新增独立模型家族。

`accepted` 必须改变该意见指定的目标字段，或首次以明确理由淘汰该候选。只改无关风险、增加无关来源、附加元数据或重复既有拒绝理由，不能替代指定字段的修复。收据列出实际变化并明确 `scientific_resolution: not_verified`；字段变化不证明科学问题已解决。已标为淘汰的候选也不能同时留在 `selected_ids` 中。

`review` 和 `revise` 的 `round` 必须取自刚读取的状态快照；过期轮次明确拒绝，避免网络重试或迟到请求被记入下一轮。初稿与综合操作不携带轮次。

综合稿候选保留 `origin: {slot, candidate_id, proposal_sha256}`，指向对应最终冻结提案。所有来源候选均须交代，包括淘汰候选；最终 ID 可统一重编，不能把不同研究者的候选来源抹掉。正式 grade 只有在完整团队过程与精确综合文件匹配时才允许通过团队契约。

当前原生入口还要求入选候选提供标准 `protocol`，后续综合提供直接父稿 SHA 和基于问题/证据/协议/可行性的实际变更记录。用 `protocol_schema` 获取权威字段；用 `report` 从最新已登记稿生成完整 `CONJECTURES.md`。报告的主稿字节、候选集合、版本和协议绑定在正式评分与最终导出时再次核对。旧嵌入式兼容开关不构成这些原生门禁的验证，详见[报告绑定](report-binding.md)和[可靠性修复](autonomous-reliability.md)。

## 记录与验证

团队状态位于管理器拥有的私有服务目录；研究者获得可读快照和提交收据。`result.json` 的 `research_team` 汇总团队过程，原生运行目录和 session 指针分别保留实际工作区、会话和恢复记录。具体状态文件名称与字段以本次实现和运行产物为准。

2026-10-18 的冻结版本 `dc4f9079a5af381666e5069c430f0693516db96a` 通过 AutoDL Linux 和 Windows 的 508 项离线测试；Windows 跳过 3 项 Unix 专用权限检查。同版真实运行完成 4 个原生会话和工作区、4 份初稿、2 轮共 8 次同伴互评与 8 次修订、2 版综合和 2 次无契约错误的正式评分。167 项产物完整性检查通过，运行期间 71 份框架源码文件保持不变。

本轮共有 10 次建议性批评，包含各研究者前期调用，不能改称综合稿另外接受了两次建议性批评。综合稿实际接受两次 CORAL 正式评阅；额外建议性批评是工作流要求中的未完成项。51 条同伴意见中 50 条标记采纳、1 条拒绝，表示已记录决议与内容变化，不表示科学上已正确解决。完整统计、评分解释、阅读范围和费用预算改动见[运行验证](native-team-validation-20261018.md)。

两次正式分数依次为 0.44（9 个 high 问题）、0.41（3 个 high 问题）；导出保留前者的精确版本。不同稿件的分数与问题数量不能直接用作质量升降结论。管理器结束后，本轮运行目录的宿主进程扫描未发现残留活动进程。

随后 2026-10-18 的 CLI 修复将未显式指定时的研究工具总预算改为 `160 × 研究者人数`，显式值仍表示整个团队的总额，并新增 1 项测试。当时 509 项离线测试在 AutoDL Linux 全部通过（33.766 秒），Windows 同版通过并跳过 3 项 Unix 专用检查（97.972 秒）。这一历史修复不改变上述真实运行的冻结版本、历史 508 项测试或 71 份源码归档；不能把该数量作为此后框架的当前测试总数。

验收需要同时核对：

1. 真实启动的研究者数量、不同 native session ID 和不同工作区，不能用批评调用次数代替 agent 数量。
2. 每位研究者的实际调研、初稿、收到与发出的互评；初稿屏障、过期版本和越权提交的拒绝记录。
3. 每轮完整的“问题 → 决议 → 修订”对应关系，以及最终综合的候选来源覆盖。
4. 综合稿 SHA、CORAL 冻结提交文件 SHA 和被评分文件 SHA 一致，并核对管理器提交身份为注册协调者；文件修改后旧综合凭证失效。
5. 同家族建议性批评、团队互评和正式 CORAL 评分分别计数，缺失研究者或未完成轮次保留 incomplete。

真实运行还要检查互评是否引出了有意义的修订或有根据的拒绝；格式和哈希检查只能验证软件契约。团队运行完成不能证明质量高于单代理，更不能替代科研实验与独立复核。

## 方法来源与边界

独立会话、工作区和持续调度来自原版 CORAL；原版 ARIS 的完整调研、构思、查新与修订技能继续交给各研究者。SAGE 的团队板补上固定轮次、冻结同伴稿、逐条决议、候选来源和综合 gate。它不是简单把旧的单次 critic 调用改名为研究 agent，也不声称调用了上游所有多岛迁移功能。

默认研究者和批评器均使用配置的 DeepSeek Flash API，同一个 API key 可以驱动多个独立会话。模型家族没有因此独立，ARIS 的跨家族独立验收仍为 `BLOCKED`，交付仍是 `provisional` 猜想。当前团队协议不自动执行真实科研实验、生成已验证论文或投稿。
